# 散歩記録API（M0 / Issue #7）

## 保存する記録

1回の散歩をセッションとし、端末がセッションとイベントのUUIDを生成する。
圏外でも同じIDで記録を保持し、通信復帰後にセッション、イベントの順で送信する。
認証、散歩の終了API、一覧・結果取得、報酬計算、一括送信は今回の対象外。

| API | リクエストの必須項目 |
| --- | --- |
| `PUT /sessions/{session_id}` | `start_datetime` |
| `PUT /sessions/{session_id}/locations/{event_id}` | `recorded_at`, `latitude`, `longitude`, `accuracy_m` |
| `PUT /sessions/{session_id}/steps/{event_id}` | `start_datetime`, `end_datetime`, `steps`, `revision` |

UUIDは再送の識別用であり、認証情報ではない。このAPIは信頼できる開発環境で検証する。
位置はWGS84の `geography(Point,4326)` として保存する。
緯度は-90〜90、経度は-180〜180、精度は0以上のメートル値を受け付ける。

## 時刻

端末の取得時刻を「いつ歩いたか」に使う。サーバーの受信時刻で置き換えない。
RFC 3339のタイムゾーン付き日時を送り、UTC・マイクロ秒精度で保存する。
マイクロ秒未満は切り捨てるため、端末もマイクロ秒以下の精度で区間を組み立てる。

サーバーは初回受信時刻を記録し、歩数の補正時には最終更新の受信時刻も記録する。
同じ内容の再送や古い更新番号の再送では、保存済みの受信時刻は変更しない。

- オフライン再送のため、記録が古いという理由では拒否しない。
- サーバー時刻から5分を超える未来の端末時刻は拒否する。
- セッション開始より前の位置・歩数区間は拒否する。
- 端末時計を戻すなどして不整合が生じた場合、無理に時刻を置き換えず送信側で確認する。

## 歩数の固定区間

セッションの開始を起点に1分ずつ区切る。区間は開始を含み、終了を含まない。
例として10:00:20開始、10:02:45終了なら、次の3レコードになる。

| start_datetime | end_datetime | 意味 |
| --- | --- | --- |
| 10:00:20 | 10:01:20 | 最初の1分 |
| 10:01:20 | 10:02:20 | 次の1分 |
| 10:02:20 | 10:02:45 | 散歩終了までの端数 |

APIは区間開始がセッション開始から整数分後であること、長さが0秒より長く1分以下で
あることを検証する。同一セッション・同一開始時刻のレコードは1件だけ保存する。
終了APIがないため、端数区間が本当に最後かは判定しない。端末は完了した1分区間と、
散歩終了時の最後の端数だけを送信する。進行中の区間を短い状態で送って後から伸ばさない。

`steps` は0以上の整数。歩数未取得・権限なし・データなしを0歩として送信しない。
それらの状態の端末内管理は #6 / #8 の接続時に扱う。

1分は保存形式の粒度であり、センサーの精度を保証するものではない。
[Android実機検証](verification/m0-i1-android-sensing.md#歩数は分単位で正確には切り出せない)
では区間の境界で歩数差が報告されている。取得元による遅延や補正を想定し、
後から同一区間の歩数を更新できるようにする。

## 再送と補正

セッションと位置の内容は保存後に変更しない。同じID・同じ内容は成功とし、
同じIDで違う内容を送ると409を返す。

歩数は最初の `revision` を1以上とし、補正するたびに増やす。
レコードID、所属セッション、開始・終了時刻は変更しない。

| 保存済みとの比較 | 結果 |
| --- | --- |
| 同じrevision・同じ歩数 | 成功、変更なし |
| 同じrevision・違う歩数 | 409、変更なし |
| 古いrevision | 成功、変更なし |
| 新しいrevision | 歩数・revision・最終受信時刻を更新 |
| 別IDで同じ区間開始 | 409、変更なし |

歩数の補正は減少も受け付ける。歩数の大小や端末時計では更新の新旧を判定しない。
再送時はID・revision・内容を変えず、送信する値を端末キューに保持する。
別IDや別セッションとして衝突を回避して送ると、意図しない重複になるため行わない。

## レスポンス

- `204`: 保存・補正・同一再送・古い歩数revisionの無視。レスポンス本文なし。
- `400`: 不正JSON、必須項目不足、時刻・座標・歩数・区間などの不正。
- `404`: 参照先のセッションが存在しない。先にセッションを送る。
- `409`: 保存済みの内容との衝突。IDやrevisionの管理を確認する。
- `503`: DBなどが利用できない。データを保持して再送する。

OpenAPIを通信形式の正とする。詳細なHTTP入力制限もOpenAPIと実装で確認する。

## 検証範囲

Goの単体テストで入力境界とエラー変換、PostGISを使うテストで空間型、
受信時刻、同一ID再送、補正、並行更新を検証する。
モバイルの1分集計・永続化・再送そのものは #6 / #8 の作業であり、
この変更だけで実機のオフラインE2Eが完成するわけではない。

### 実PostGISテストを実行する

通常の `task api:test` はDB接続を必要とするテストをスキップする。
ローカル開発用PostGISを起動して、接続先を明示するとDBテストも実行できる。

```sh
task db:up
task db:migrate
cd api
TEST_DATABASE_URL='postgres://teku_dun:teku_dun@127.0.0.1:5432/teku_dun?sslmode=disable' \
  go test -race ./internal/walk/... ./internal/httpapi
```

接続先には検証専用DBを使う。テストは専用スキーマを作成して削除するため、
接続ユーザーにはその権限が必要。通常のアプリ用テーブルはテストで削除しない。
`TestWalkHTTPPostGIS` は生成ルーターへJSONを送信し、レスポンスとDB行の両方を確認する。
緯度・経度の保存順序、SRID、端末時刻と受信時刻、重複行が増えないこと、
減少補正後に古い再送が届いても歩数が戻らないことを検証する。
