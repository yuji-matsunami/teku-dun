# 技術選定

## 前提

本書は [アプリの方向性](product-overview.md) と [MVPスコープ](mvp-scope.md) を実現するための技術構成をまとめたものである。

選定にあたって置いた前提は次のとおり。

- 開発体制は2人。フロントエンドの経験は浅い。
- バックエンドは Go を書き慣れている。
- iOS と Android の両方を対象とする。
- サーバは自前のAPIとデータベースを持つ。
- 地図と場所データは、従量課金の少ない OpenStreetMap 系を優先する。
- 費用を極力抑える。MVPの検証が終わるまで固定費をほぼゼロに保つ。

## 選定方針

このアプリの技術的な難所は、RPG部分ではなく次の3点に集中する。

1. 画面を見ずに遊べる前提を満たす、バックグラウンドでの位置情報と歩行の計測
2. 車や電車による移動を徒歩として扱わないための判別
3. 自宅周辺でも成立し、かつ危険な場所を避ける目的地の自動生成

戦闘計算や装備管理は一般的なCRUDとロジックであり、技術的な冒険をする理由がない。したがって、上記3点に人的リソースを集中できる構成を選ぶ。

具体的には次の方針を取る。

- 2人で2つのOSを個別に開発しない。クロスプラットフォームで1つのコードベースに統一する。
- 外部APIへの従量課金を、リクエストのたびに発生させない設計にする。
- 有料の判断は、無償で検証しきれないと分かった時点まで先送りする。ただし、後から乗り換えられない選択だけは最初に正しく決める。
- ゲームの進行判定はサーバ側に置く。

## モバイルアプリ

### Flutter を採用する

理由は次のとおり。

- 2人体制で iOS と Android のネイティブUIを別々に保守することは現実的でない。
- React Native は React とWebエコシステムの知識を前提とする度合いが強く、フロントエンドの経験が浅い体制ではむしろ学習コストが高い。
- Flutter は Dart だけで完結し、静的型付けである点で Go の書き味に近い。UIコンポーネントが公式に揃っているため、デザイン経験が浅くても一定の見た目になる。
- 戦闘結果やアイテム獲得の演出など、アニメーション表現を標準機能で作りやすい。本格的なゲーム表現が必要になった場合も、Flame を部分的に埋め込める。
- 本アプリで必須となる位置情報、ジオフェンス、ヘルスデータのプラグインが揃っている。

Kotlin Multiplatform と Compose Multiplatform も候補になるが、iOS側の成熟度とプラグインの選択肢で Flutter に劣る。2人体制で採る冒険ではないため見送る。

### 端末内DB

散歩中は圏外や電波の弱い場所を通る。位置サンプルと未送信のイベントは Drift (SQLite) にバッファし、通信が回復したときにまとめて送信する。

装備やインベントリのマスタデータもキャッシュし、散歩中にサーバへ問い合わせずに画面を描画できるようにする。

## バックエンド

### Go + chi

Web フレームワークは薄いものでよい。`net/http` と chi のルーティングで足りる。ORM は使わず sqlc を採用する。PostGIS の空間クエリは生のSQLで書く必要があり、ORM を挟むと不利になるためである。

### PostgreSQL + PostGIS

PostGIS は本構成の中核である。次の処理をすべてデータベース側で行う。

- 現在地から徒歩圏内にある目的地候補の抽出
- 目的地への到着判定に使う距離計算
- 歩行軌跡の保存と、移動距離の算出

MVPの規模では、専用の地理空間サービスを別途用意する必要はない。

### 進行判定はサーバに置く

装備のドロップ、戦闘の勝敗、強敵へ与えたダメージは、すべてサーバ側で計算して確定させる。クライアントは位置サンプルの列と経過時間を送り、サーバがその妥当性を検証したうえで結果を返す。

MVPの時点では厳しい不正対策までは行わないが、判定ロジックを最初からサーバに置いておけば、後から検証を強化できる。逆に、端末側で確定させる設計にすると後戻りできない。

### 認証

MVPでは端末が生成する匿名アカウントとし、JWT でセッションを維持する。ソーシャルログインは設けない。

機種変更時の引き継ぎが必要になった段階で Sign in with Apple と Google を追加する。なお、サードパーティのログイン手段を1つでも提供する場合、App Store の審査要件により Sign in with Apple の実装が必要になる点に注意する。

## 地図と場所データ

### 地図表示

MapLibre GL を採用する。API キーなしで動作し、タイルの配信元を自分で選べる。ベクタータイルに対応しているため、現実の地図をファンタジー世界に見立てた独自スタイルを適用できる。世界観の演出上、これは大きな利点になる。

`flutter_map` はラスタータイル前提であり、ベクタースタイルの適用は追加プラグインに依存する。MapLibre GL を直接使うほうが素直である。

### タイル配信

Protomaps が公開している OpenStreetMap のビルドから必要な範囲だけを抽出し、PMTiles 形式の単一ファイルとして Cloudflare R2 に配置する。MapLibre は Range リクエストで必要な部分だけを取得するため、地図サーバを運用する必要がない。

商用の地図APIは表示回数に応じて課金されるため、歩くたびに地図を見るこのアプリとは相性が悪い。PMTiles と R2 の組み合わせなら、利用が伸びても費用が保管料だけに留まる。

抽出範囲は最初から日本全域にしない。検証で歩く地域だけを抽出すればファイルは小さくなり、R2 の無償枠（10GB）に確実に収まる。範囲は `pmtiles extract` で後から広げられるため、必要になってから広げればよい。

### POI（目的地に使う場所データ）

**Overpass API を実行時に呼び出す設計は採らない。** 公開インスタンスはボランティア運営であり、アプリからの継続的な呼び出しは利用ポリシー上認められていない。

代わりに、次の方式を取る。

1. Geofabrik が配布する日本の OSM データを取得する。
2. `osm2pgsql` で自前の PostGIS へ取り込む。
3. 公園、神社、広場、コンビニ、交差点など、目的地に使えるタグだけを抽出した専用テーブルを作る。
4. 目的地生成は、このテーブルへの空間検索だけで行う。

**MVPでは取り込み範囲を、検証で歩く都道府県だけに絞る。** 日本全域を丸ごと取り込むとデータベースの無償枠に収まらず、取り込みにも時間がかかる。一方で、MVPの検証に必要なのは開発者2人が実際に歩く範囲だけである。

範囲を絞ることで次の利点が得られる。

- Neon の無償枠（0.5GB）に収まり、データベース費用がゼロで済む
- 取り込みが短時間で終わり、タグの抽出条件を何度も試せる
- 目的地の品質を、実際に歩いて確認できる範囲に限定して評価できる

対象地域はテーブルの行を入れ替えるだけで広げられるため、後戻りにはならない。

この方式には副次的な利点がある。安全性とプライバシーの原則に挙げた「私有地や立入禁止区域を目的地にしない」という要件は、外部APIの検索結果に対しては制御しきれないが、自前テーブルであれば取り込み時に `access=private` や高速道路沿いを除外でき、フィルタ条件を自分たちで育てていける。

## 位置情報と歩行の計測

本アプリで最も難易度が高い領域であり、ここでの手戻りが最も高くつく。

### バックグラウンド位置

この領域だけは自作を勧めない。停止中のGPS停止、OEMごとの省電力挙動、圏外時の永続化と再送といった作り込みが品質を決め、2人体制で再実装すると本体の開発時間を失う。

候補は3つある。

| 候補 | 費用 | 評価 |
| --- | --- | --- |
| `flutter_background_geolocation` | 買い切り $399（1アプリ、iOS/Android共通） | 実績は最も厚い。DEBUGビルドは無償で、30日の試用ライセンスもある |
| `tracelet` | 無償（Apache-2.0） | 同等の機能を掲げる新興パッケージ。採用実績は上記より大幅に少ない |
| `geolocator` + `flutter_foreground_task` | 無償 | 部品しか提供されない。省電力と欠損対策を自作することになる |

**費用の判断は先送りできる。** `flutter_background_geolocation` はDEBUGビルドなら無償で完全に動作するため、プロトタイプから計測精度の検証までは1円もかけずに進められる。支払いが必要になるのは、ストアへ配信するリリースビルドを作る段階である。

したがって、次の順序を取る。

1. まず `flutter_background_geolocation` のDEBUGビルドで計測精度を確かめる。この時点では無償である。
2. 並行して `tracelet` を同じ端末で試し、精度とバッテリー消費を比較する。無償で置き換えられるなら $399 を払わずに済む。
3. 配信の直前に、比較結果を見て購入するかどうかを決める。

なお、pub.dev の説明では有償ライセンスが必要なのは Android のリリースビルドのみとされている一方、販売ページでは「1つのライセンスが iOS と Android の両方をカバーする」と記載されており、iOS単体配信で無償になるかは読み取れない。iOS先行で費用を抑える前提を置く場合は、事前に販売元へ確認する。

3番目の自作案は、費用ゼロに見えて最も高くつく。ここは削るべきコストではない。

### 歩数

`health` パッケージ経由で、iOS は HealthKit、Android は Health Connect から歩数を取得する。Google Fit API は提供が終了しているため、Android は Health Connect を前提とする。

### 徒歩と車・電車の判別

歩数だけでは判別できず、位置情報だけでも不十分である。次の3つを組み合わせて判定する。

- 端末の活動種別（iOS の CoreMotion、Android の Activity Recognition API）
- 位置サンプルから算出した移動速度
- 歩数と移動距離の整合性

判定はサーバ側で行う。クライアントは観測値をそのまま送る。

MVPでは、判定条件は緩く始めて実測データを集め、そのうえで閾値を決める。判定に使うログを最初から保存しておくことを設計に含める。

### プラットフォーム固有のリスク

- iOS では常時許可（Always）の位置情報権限が必要になる。App Store の審査では用途の説明が求められるため、審査提出前に説明文と実装を揃えておく。
- Android ではフォアグラウンドサービスの位置情報タイプ宣言と、Google Play Console でのバックグラウンド位置情報の利用申請が必要になる。申請には審査期間があるため、リリース直前に着手すると間に合わない。
- 上記2点は開発の最終盤ではなく、プロトタイプ段階で一度通しておく。

## インフラ

Cloud SQL は最小構成でも常時課金が発生するため、MVPでは採用しない。次の構成で固定費をほぼゼロにする。

| 用途 | 採用 | 費用 |
| --- | --- | --- |
| APIサーバ | Cloud Run | 無償枠内。リクエストがなければゼロにスケールする |
| データベース | Neon (PostgreSQL) | 無償枠内。PostGIS が使え、ゼロにスケールする。ストレージ 0.5GB |
| タイル・静的アセット | Cloudflare R2 | 無償枠内。ストレージ10GBまで、転送量は課金されない |

**タイル配信先に R2 を指定するのは、転送量課金がゼロだからである。** 地図タイルは利用者が歩くたびに繰り返し取得される。一般的なオブジェクトストレージでは、この転送量がそのまま費用になる。R2 はこれがかからないため、利用が伸びても保管料だけで済む。ここは他社に置き換えないほうがよい。

Neon のストレージ上限 0.5GB は、後述するPOIの取り込み範囲を絞ることで収まる。

無償枠に収まらなくなった場合は、VPS1台（Hetzner CX22 で月額 €3.79 程度）へ Go と PostgreSQL をまとめて載せるのが次の選択肢になる。マネージドサービスを使い続けるより安く、上限もない。移行できるよう、DBには特定ベンダー固有の機能を使わない。

## 開発体制と分担

| 担当 | 範囲 |
| --- | --- |
| モバイル | Flutter アプリ、地図表示、位置情報と歩数の取得、UI |
| サーバ | Go API、PostGIS、OSM取り込み、ゲームロジック、インフラ |

2人の接点は API のみとする。OpenAPI で定義を1つ置き、Go 側は `oapi-codegen`、Dart 側はコード生成でクライアントを作る。定義を先に決めれば、互いの完成を待たずに並行して進められる。

## 費用

### 検証段階は無償で完結させる

MVPの目的は「ゲームの続きのために散歩に出るか」を確かめることであり、これは開発者2人の実機で検証できる。ストアに配信しなければ、次のとおり費用はかからない。

| 項目 | 検証段階 | ストア配信段階 |
| --- | --- | --- |
| バックグラウンド位置ライブラリ | ¥0（DEBUGビルドは無償） | $0〜$399（買い切り・1アプリ） |
| APIサーバ（Cloud Run） | ¥0 | ¥0〜 |
| データベース（Neon） | ¥0 | ¥0〜 |
| 地図タイル（R2） | ¥0 | ¥0 |
| 地図・POIデータ（OSM） | ¥0 | ¥0 |
| Google Play デベロッパー登録 | 不要 | $25（買い切り） |
| Apple Developer Program | 不要 | $99（年額） |

つまり、**検証が終わるまでの固定費はゼロにできる。** 支出が発生するのは、ストアに出すと決めた時点である。

### 検証は Android 実機を先行させる

費用の観点では Android が有利である。

- Android は DEBUG ビルドの APK を自分の端末へ直接入れられる。期限も追加費用もない。
- iOS は無料のプロビジョニングだとビルドが7日で失効し、利用できるCapabilityにも制限がある。継続的な実機検証には Apple Developer Program の年額 $99 が実質必要になる。
- ストア登録料も、Google Play は $25 の買い切り、Apple は $99 の年額と差が大きい。

ただし、これは費用だけを見た場合の結論である。技術的には Android のほうが難しい。端末メーカーごとの省電力制御でバックグラウンド計測が止まりやすく、Google Play のバックグラウンド位置情報の利用申請も通しにくい。

そのため、**Android で先行して無償で検証しつつ、iOS の審査要件の確認だけは後回しにしない**という進め方を取る。iOS の年額を払うのは、Android での検証で中心体験が成立すると分かってからでよい。

### 費用をかけるべき唯一の箇所

削ってはいけないのはバックグラウンド位置ライブラリである。ここを自作して浮く $399 に対し、失う開発時間と品質リスクが見合わない。ただし前述のとおり支払いは配信直前まで先送りでき、`tracelet` が使えれば不要になる可能性もある。

それ以外は、無償枠と OSM で十分に賄える。

## 主要な技術リスク

| リスク | 内容 | 対応 |
| --- | --- | --- |
| バックグラウンド計測 | OSの制限とバッテリー消費により、歩行が正しく記録されない | 最優先で実機検証する。実装よりも先に計測精度を確かめる |
| ストア審査 | 常時位置情報の許可とバックグラウンド位置の申請が通らない | プロトタイプ段階で一度審査を通し、期間と要件を把握する |
| 目的地の品質 | 住宅地でOSMのPOIが乏しく、目的地を生成できない | 開発者の自宅周辺を含む複数地域で候補数を実測してから判定条件を決める |
| 安全性 | 危険な場所や私有地が目的地になる | 取り込み時の除外条件を設計項目として扱い、実地で確認する |
| バランス調整 | 数値の調整にアプリ更新が必要になる | ドロップ率や強敵の性能はサーバ設定として持ち、更新なしで変更できるようにする |

このうち上2つは、実装量ではなく可否を左右する。**プロトタイプの最初の作業は、ゲーム部分ではなく「散歩の軌跡を正しく記録し、サーバへ送る」ことに置く。**

## 未決事項

- `tracelet` が `flutter_background_geolocation` の代替として実用に足るか
- `flutter_background_geolocation` を iOS 単体で配信する場合にライセンスが不要か（販売元への要確認事項）
- 検証を Android 先行にするか、iOS 先行にするか
- OSM データの更新頻度と取り込みの運用方法
- 地図スタイルを独自制作するか、既存スタイルの改変から始めるか
- 検証用イベントログを自前テーブルで持つか、分析サービスを使うか
