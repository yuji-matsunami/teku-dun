# 技術選定

## 前提

本書は [アプリの方向性](product-overview.md) と [MVPスコープ](mvp-scope.md) を実現するための技術構成をまとめたものである。

選定にあたって置いた前提は次のとおり。

- 開発体制は2人。フロントエンドの経験は浅い。
- バックエンドは Go を書き慣れている。
- iOS と Android の両方を対象とする。
- サーバは自前のAPIとデータベースを持つ。
- 地図と場所データは、従量課金の少ない OpenStreetMap 系を優先する。

## 選定方針

このアプリの技術的な難所は、RPG部分ではなく次の3点に集中する。

1. 画面を見ずに遊べる前提を満たす、バックグラウンドでの位置情報と歩行の計測
2. 車や電車による移動を徒歩として扱わないための判別
3. 自宅周辺でも成立し、かつ危険な場所を避ける目的地の自動生成

戦闘計算や装備管理は一般的なCRUDとロジックであり、技術的な冒険をする理由がない。したがって、上記3点に人的リソースを集中できる構成を選ぶ。

具体的には次の方針を取る。

- 2人で2つのOSを個別に開発しない。クロスプラットフォームで1つのコードベースに統一する。
- 実績のあるライブラリを選び、有料でも解決するものは購入する。
- 外部APIへの従量課金を、リクエストのたびに発生させない設計にする。
- ゲームの進行判定はサーバ側に置く。

## モバイルアプリ

### Flutter を採用する

理由は次のとおり。

- 2人体制で iOS と Android のネイティブUIを別々に保守することは現実的でない。
- React Native は React とWebエコシステムの知識を前提とする度合いが強く、フロントエンドの経験が浅い体制ではむしろ学習コストが高い。
- Flutter は Dart だけで完結し、静的型付けである点で Go の書き味に近い。UIコンポーネントが公式に揃っているため、デザイン経験が浅くても一定の見た目になる。
- 戦闘結果やアイテム獲得の演出など、アニメーション表現を標準機能で作りやすい。本格的なゲーム表現が必要になった場合も、Flame を部分的に埋め込める。
- 本アプリで必須となる位置情報、ジオフェンス、ヘルスデータのプラグインが揃っている。

Kotlin Multiplatform と Compose Multiplatform も候補になるが、iOS側の成熟度とプラグインの選択肢で Flutter に劣る。2人体制で採る冒険ではないため見送る。

### 端末内DB

散歩中は圏外や電波の弱い場所を通る。位置サンプルと未送信のイベントは Drift (SQLite) にバッファし、通信が回復したときにまとめて送信する。

装備やインベントリのマスタデータもキャッシュし、散歩中にサーバへ問い合わせずに画面を描画できるようにする。

## バックエンド

### Go + chi

Web フレームワークは薄いものでよい。`net/http` と chi のルーティングで足りる。ORM は使わず sqlc を採用する。PostGIS の空間クエリは生のSQLで書く必要があり、ORM を挟むと不利になるためである。

### PostgreSQL + PostGIS

PostGIS は本構成の中核である。次の処理をすべてデータベース側で行う。

- 現在地から徒歩圏内にある目的地候補の抽出
- 目的地への到着判定に使う距離計算
- 歩行軌跡の保存と、移動距離の算出

MVPの規模では、専用の地理空間サービスを別途用意する必要はない。

### 進行判定はサーバに置く

装備のドロップ、戦闘の勝敗、強敵へ与えたダメージは、すべてサーバ側で計算して確定させる。クライアントは位置サンプルの列と経過時間を送り、サーバがその妥当性を検証したうえで結果を返す。

MVPの時点では厳しい不正対策までは行わないが、判定ロジックを最初からサーバに置いておけば、後から検証を強化できる。逆に、端末側で確定させる設計にすると後戻りできない。

### 認証

MVPでは端末が生成する匿名アカウントとし、JWT でセッションを維持する。ソーシャルログインは設けない。

機種変更時の引き継ぎが必要になった段階で Sign in with Apple と Google を追加する。なお、サードパーティのログイン手段を1つでも提供する場合、App Store の審査要件により Sign in with Apple の実装が必要になる点に注意する。

## 地図と場所データ

### 地図表示

MapLibre GL を採用する。API キーなしで動作し、タイルの配信元を自分で選べる。ベクタータイルに対応しているため、現実の地図をファンタジー世界に見立てた独自スタイルを適用できる。世界観の演出上、これは大きな利点になる。

`flutter_map` はラスタータイル前提であり、ベクタースタイルの適用は追加プラグインに依存する。MapLibre GL を直接使うほうが素直である。

### タイル配信

Protomaps が公開している OpenStreetMap のビルドから日本の範囲だけを抽出し、PMTiles 形式の単一ファイルとしてオブジェクトストレージに配置する。MapLibre は Range リクエストで必要な部分だけを取得するため、地図サーバを運用する必要がない。費用は保管料と転送量のみに収まる。

商用の地図APIを使う場合と比べ、利用が伸びても費用が線形に跳ね上がらない点で、この構成を優先する。

### POI（目的地に使う場所データ）

**Overpass API を実行時に呼び出す設計は採らない。** 公開インスタンスはボランティア運営であり、アプリからの継続的な呼び出しは利用ポリシー上認められていない。

代わりに、次の方式を取る。

1. Geofabrik が配布する日本の OSM データを定期的に取得する。
2. `osm2pgsql` で自前の PostGIS へ取り込む。
3. 公園、神社、広場、コンビニ、交差点など、目的地に使えるタグだけを抽出した専用テーブルを作る。
4. 目的地生成は、このテーブルへの空間検索だけで行う。

この方式には副次的な利点がある。安全性とプライバシーの原則に挙げた「私有地や立入禁止区域を目的地にしない」という要件は、外部APIの検索結果に対しては制御しきれないが、自前テーブルであれば取り込み時に `access=private` や高速道路沿いを除外でき、フィルタ条件を自分たちで育てていける。

## 位置情報と歩行の計測

本アプリで最も難易度が高い領域であり、ここでの手戻りが最も高くつく。

### バックグラウンド位置

`flutter_background_geolocation` を採用する。モーション検知と連動して停止中はGPSを止めるなど、バッテリー消費を抑える実装が作り込まれており、ジオフェンスと未送信データの永続化も備えている。

このライブラリは iOS では無償で利用でき、Android のリリースビルドについてのみ有償ライセンスが必要になる。自前で同等の実装を作る場合の工数と品質リスクを考えれば、購入する価値がある。2人体制であればなおさら、ここは買って時間を確保するべきである。

無償で進める場合は `geolocator` と `flutter_foreground_task` を組み合わせることになるが、バッテリー消費と計測の欠損を自力で作り込む必要がある。

### 歩数

`health` パッケージ経由で、iOS は HealthKit、Android は Health Connect から歩数を取得する。Google Fit API は提供が終了しているため、Android は Health Connect を前提とする。

### 徒歩と車・電車の判別

歩数だけでは判別できず、位置情報だけでも不十分である。次の3つを組み合わせて判定する。

- 端末の活動種別（iOS の CoreMotion、Android の Activity Recognition API）
- 位置サンプルから算出した移動速度
- 歩数と移動距離の整合性

判定はサーバ側で行う。クライアントは観測値をそのまま送る。

MVPでは、判定条件は緩く始めて実測データを集め、そのうえで閾値を決める。判定に使うログを最初から保存しておくことを設計に含める。

### プラットフォーム固有のリスク

- iOS では常時許可（Always）の位置情報権限が必要になる。App Store の審査では用途の説明が求められるため、審査提出前に説明文と実装を揃えておく。
- Android ではフォアグラウンドサービスの位置情報タイプ宣言と、Google Play Console でのバックグラウンド位置情報の利用申請が必要になる。申請には審査期間があるため、リリース直前に着手すると間に合わない。
- 上記2点は開発の最終盤ではなく、プロトタイプ段階で一度通しておく。

## インフラ

Cloud Run と Cloud SQL for PostgreSQL を採用する。2人体制でサーバ運用に時間を割かないことを優先し、コンテナを置くだけで動く構成にする。PostGIS は Cloud SQL の拡張として利用できる。

タイルの PMTiles と静的アセットはオブジェクトストレージへ置く。

## 開発体制と分担

| 担当 | 範囲 |
| --- | --- |
| モバイル | Flutter アプリ、地図表示、位置情報と歩数の取得、UI |
| サーバ | Go API、PostGIS、OSM取り込み、ゲームロジック、インフラ |

2人の接点は API のみとする。OpenAPI で定義を1つ置き、Go 側は `oapi-codegen`、Dart 側はコード生成でクライアントを作る。定義を先に決めれば、互いの完成を待たずに並行して進められる。

## 主要な技術リスク

| リスク | 内容 | 対応 |
| --- | --- | --- |
| バックグラウンド計測 | OSの制限とバッテリー消費により、歩行が正しく記録されない | 最優先で実機検証する。実装よりも先に計測精度を確かめる |
| ストア審査 | 常時位置情報の許可とバックグラウンド位置の申請が通らない | プロトタイプ段階で一度審査を通し、期間と要件を把握する |
| 目的地の品質 | 住宅地でOSMのPOIが乏しく、目的地を生成できない | 開発者の自宅周辺を含む複数地域で候補数を実測してから判定条件を決める |
| 安全性 | 危険な場所や私有地が目的地になる | 取り込み時の除外条件を設計項目として扱い、実地で確認する |
| バランス調整 | 数値の調整にアプリ更新が必要になる | ドロップ率や強敵の性能はサーバ設定として持ち、更新なしで変更できるようにする |

このうち上2つは、実装量ではなく可否を左右する。**プロトタイプの最初の作業は、ゲーム部分ではなく「散歩の軌跡を正しく記録し、サーバへ送る」ことに置く。**
