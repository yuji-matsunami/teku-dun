# M0-I1 Android バックグラウンド位置・Health Connect 収集の検証

## 検証アプリの設計

同一アプリ内でバックグラウンド位置ライブラリを切り替えられるようにし、
**両候補を同一端末・同一フォーマットのログで比較できる**ようにする。

```
[ UI ]  プロバイダ選択 / 権限 / セッション開始・停止 / 集計表示 / エクスポート
   |
[ LocationProvider (抽象) ]
   |-- FbgLocationProvider      : flutter_background_geolocation
   |-- TraceletLocationProvider : tracelet
   |
   v
[ LocationSample (共通スキーマ) ] --> [ JsonlLogSink ] --> sessions/<id>/events.jsonl
                                                            + meta.json
   ^
[ HealthStepsReader ] Health Connect の歩数
[ BatterySampler ]    電池残量
```

比較を成立させるうえで重要な点は次の3つ。

1. **共通スキーマに正規化する。** 各ライブラリの位置オブジェクトはフィールド名も単位も異なる。
   受け取った直後に `LocationSample` へ変換し、以降は同じ経路で扱う。
2. **1行1レコードの JSONL へ即時 flush する。** 散歩中に OS がアプリを停止させても、
   そこまでのログが残る。まとめ書きにすると欠損の有無自体が測れない。
3. **集計はアプリ内で行う。** 散歩から戻った直後に取得間隔・欠損・電池消費が読めれば、
   比較表をその場で埋められる。

## 予備検証（bg_test）で判明したこと

本番の比較計測に入る前に、`flutter_background_geolocation` 単体が実機で動くかを
別アプリ（`bg_test`）で確認した。以下はそのときに得られた事実である。

### 実施条件

| 項目 | 値 |
| --- | --- |
| 端末 | Samsung SC-51D |
| Android | 16 |
| 実施日 | 2026-08-22 |
| ライブラリ | flutter_background_geolocation 5.5.0（DEBUGビルド） |
| 設定 | `distanceFilter: 0`、`stopOnTerminate: false`、`startOnBoot: true` |

### 判明したこと

| 項目 | 結果 |
| --- | --- |
| 位置情報の取得 | 成立。精度 4〜8m |
| 取得間隔 | 約1秒 |
| 位置情報の権限 | **「常に許可」が必須。** 「アプリの使用中のみ」ではバックグラウンドで取得できない |
| モーション判定 | 動作（`DetectedActivity [type=STILL, confidence=100]`、isMoving の遷移を確認） |
| アプリ終了後のネイティブ側 | **記録を継続**（`MainActivity was destroyed` / `stopOnTerminate: false` / `enabled: true`） |
| DEBUGビルドのライセンス | 不要。警告なく全機能が動作 |

### 取得間隔が約1秒になった理由

`distanceFilter: 0` にしたためである。fbg は `distanceFilter` が
`locationUpdateInterval` を上書きする仕様で、0 にして初めて時間駆動になる。

**本検証アプリは両ライブラリを揃えるため `distanceFilter: 10m` にしてあるので、
fbg は移動距離駆動になり、この1秒間隔にはならない。** 比較表を読むときに
この違いを取り違えないこと。

### `enableHeadless: true` だけでは動かない

`bg_test` では `enableHeadless: true` を設定していたが、
`registerHeadlessTask()` を呼んでいなかった。その結果、ログには

```
☯️  HeadlessMode? true
💀 [HeadlessTask terminate]
🔴  Cleared callbacks
```

と出るものの、**アプリ終了後は Dart 側で一切何も記録されなかった。**
設定とコールバック登録の両方が必要である。本検証アプリでは
`main()` で両ライブラリのヘッドレスタスクを登録している。

### ログの取り方に関する注意

`adb logcat | grep flutter` は **Dart 側の出力しか拾わない。**
アプリが終了するとネイティブが記録を続けていても何も出なくなるため、
これだけを見て「計測が止まった」と判断してはいけない。

- ネイティブの動作を見る: `adb logcat | grep TSLocationManager`
- 確実なのは、本検証アプリのセッション詳細画面で
  「プラグイン内部記録との突き合わせ」と「ヘッドレス記録件数」を確認すること

## 手順

### 前提

| 項目 | 条件 |
| --- | --- |
| 端末 | Android 8.0 (API 26) 以上の実機。エミュレータでは意味のある結果が出ない |
| Health Connect | Android 14 未満は Play ストアからのインストールが必要。アプリ内に導線がある |
| 歩数の供給元 | Health Connect 自体は歩数を作らない。Fitbit、Google Fit、端末標準の健康アプリなど、歩数を書き込むアプリが1つ必要 |
| ビルド | DEBUG ビルドのみ。`flutter_background_geolocation` は DEBUG ならライセンス不要 |
| 開発環境 | Flutter 3.47.1 / Dart 3.13.1 で確認済み |

### 1. アプリを端末へ入れる

```
cd spikes/android_sensing_spike
flutter pub get
flutter run            # 端末を接続した状態で
```

APK だけ作る場合は次を実行し、`build/app/outputs/flutter-apk/app-debug.apk` を端末へ転送する。

```
flutter build apk --debug
```

### 2. 権限を許可する

アプリの「権限をリクエスト」を押し、順に許可する。

1. 位置情報 — **「正確な位置情報」かつ「常に許可」** を選ぶ
2. 身体活動
3. 通知
4. Health Connect の歩数読み取り

Android では「常に許可」を最初のダイアログで選べない。まず「アプリの使用中のみ許可」を選び、
そのあとに再度出るダイアログ、または設定画面から「常に許可」へ格上げする必要がある。
アプリはこの順序でリクエストするようになっている。

### 3. 電池最適化を外す

端末の設定から、本アプリを電池最適化の対象外にする。

```
設定 > アプリ > android_sensing_spike > バッテリー > 制限なし
```

メーカー独自の省電力機能（Samsung のスリープ中のアプリ、Xiaomi の自動起動管理など）も
併せて解除する。**ここを外さないと、計測が止まったのが OS の制限によるものか
ライブラリの問題かを切り分けられない。**

### 4. 1回目の計測（flutter_background_geolocation）

1. プロバイダで `flutter_background_geolocation` を選ぶ
2. **充電ケーブルを抜く**（挿したままだと電池消費を比較できない）
3. 開始ボタンを押す
4. 画面をロックし、端末をポケットへ入れる
5. **10〜15分歩く**
6. 戻ったら端末を取り出し、停止ボタンを押す

歩行中に画面を点けて確認する必要はない。むしろ画面を点けると、
「画面ロック中も動くか」という検証条件が崩れる。

### 5. 2回目の計測（tracelet）

同じ経路を、同じ条件でもう一度歩く。プロバイダだけ `tracelet` へ切り替える。

比較を成立させるため、次を揃える。

- 同じ端末
- 同じ経路と歩行速度
- 同じポケット位置（体のどちら側か、上着か下か）
- 開始時の電池残量が近いこと
- 天候と時間帯が大きく違わないこと

アプリ側の計測設定（精度 high、distanceFilter 10m、更新間隔 5000ms、
`stopOnTerminate: false`、`startOnBoot: false`）は両プロバイダで同一にしてある。

### 6. 結果を読む

「セッション一覧」から各セッションを開くと、集計が表示される。

| 表示 | 意味 |
| --- | --- |
| 件数 | 取得できた位置サンプル数 |
| 取得間隔（中央値 / p95 / 最大） | 最大値がそのまま**最大欠損時間**になる |
| 欠損区間 | 60秒を超えて位置が取れなかった区間の一覧 |
| 欠損率 | 計測時間のうち欠損が占める割合 |
| 移動距離 | 精度50m超のサンプルを除外して積算した距離 |
| 精度（中央値 / p95） | 位置精度のメートル値 |
| 電池消費 | 開始・終了時の残量差と、1時間あたりの換算値 |
| 活動種別 | 歩行・車両などの判定内訳 |

この値をそのまま本書の「比較結果」表へ転記する。


### 「計測が死んだ」と「アプリだけ落ちた」の切り分け

両ライブラリとも `stopOnTerminate: false` で動くため、Android が Flutter の
Dart プロセスを停止させても、ネイティブ側のサービスは記録を続ける。
一方このアプリの JSONL ログは Dart 側でしか書けないため、
この場合ログだけが途切れる。

ログの見た目だけでは「ライブラリが計測を止めた」場合と区別がつかない。
取り違えると、実際には正常に動いていたライブラリを不採用にしかねない。

そこでセッション終了時に、プラグイン内部のDBの記録件数を読み出して
自前ログと突き合わせ、結果を画面に表示する。

| 突き合わせ結果 | 意味 |
| --- | --- |
| 両者がほぼ一致 | Dart 側の取りこぼしは無い。ログの欠損はそのままライブラリ側の挙動 |
| プラグイン側が大幅に多い | **アプリだけが落ち、ライブラリは動いていた。** ライブラリの問題ではない |
| 両者とも少ない | ライブラリまたは OS が計測を止めた |

なお `flutter_background_geolocation` は使い捨てサンプルを自前DBへ保存しないため、
両者の件数は元々完全には一致しない。大きく乖離しているかどうかで判断する。

### 集計値を読むときの注意

| 表示 | 注意点 |
| --- | --- |
| 最大取得間隔(サンプル間) | サンプルとサンプルの最大の空き。頭尾の欠損は含まない |
| 最大欠損 | 頭尾を含めた最大の欠損。**計測が途中で死んだ場合はここに出る** |
| 欠損の内訳 | 「開始直後」はGPSの初期補足で正常時も出る。「終了直前」は計測が止まった疑いが濃い |
| この計測区間の歩数 | ホーム画面の計測前の表示は当日累計なので混同しない |

`flutter_background_geolocation` の `locationUpdateInterval` は
`distanceFilter > 0` のとき無効になる（公式仕様）。
本アプリは両者とも `distanceFilter` 10m で揃えているため、
fbg は移動距離駆動で発火する。**取得間隔の差をそのままライブラリの性能差と
読まないこと。**

### 7. 権限拒否時の挙動を確認する

受け入れ条件に含まれるため、許可した場合だけでなく拒否した場合も確認する。

1. 設定からアプリの権限をすべて取り消す
2. アプリを再起動する
3. 位置情報を「許可しない」で拒否 → 画面の表示とログを確認する
4. 位置情報を「アプリの使用中のみ許可」に留める → 画面ロック後に取得が止まるかを確認する
5. Health Connect の歩数を拒否 → 歩数取得の失敗がどう表示されるかを確認する

いずれの場合もアプリが落ちないこと、および何が拒否されたか画面から判別できることを確認する。

### 8. ログを取り出す

セッション一覧の共有ボタンから `events.jsonl` を書き出せる。
`adb` で直接取り出す場合は次のとおり。

```
adb exec-out run-as jp.tekudun.android_sensing_spike \
  cat files/sessions/<セッションID>/events.jsonl > events.jsonl
```

### ログの形式

1行1レコードの JSONL。位置サンプルとイベントが同じ時系列に混ざって並ぶため、
「いつ権限が変わったか」「いつアプリがバックグラウンドへ回ったか」を
位置の欠損と突き合わせて読める。

```json
{"type":"location","seq":1,"providerId":"fbg","recordedAt":"...","receivedAt":"...","latitude":35.68,"longitude":139.76,"accuracy":8.5,"isMoving":true,"activity":"on_foot","activityConfidence":87,"batteryLevelPercent":92}
{"type":"event","at":"...","kind":"healthSnapshot","totalSteps":1234,"sourceApps":["..."]}
{"type":"event","at":"...","kind":"appLifecycle","state":"paused"}
```

計測データそのものはリポジトリへコミットしない（`.gitignore` で `*.jsonl` を除外している）。
結果は本書の比較表へ数値として転記する。

## 比較結果

### 実施規模

2026-08-23 から 08-27 にかけて、以下を計測した。

| 項目 | 値 |
| --- | --- |
| 計測セッション | 17件（fbg 9 / tracelet 8） |
| 総計測時間 | 約14時間 |
| 位置サンプル | 約2,700件 |
| 端末 | Samsung SC-51D（Android 16 / SDK 36） |
| ビルド | DEBUG のみ。費用ゼロ |

初期のセッションには電車や車での移動が混ざっており、徒歩の比較には使えていない。
移動手段は、活動種別ではなく**区間速度の実測値**で判別した。

### 徒歩での対比較（主結果）

08-27 に、同一の周回路を連続した時間帯に1周ずつ歩いたもの。
始終点がほぼ一致しており（fbg 14m差、tracelet 1m差）、条件が最もよく揃っている。

| 観点 | `flutter_background_geolocation` | `tracelet` |
| --- | --- | --- |
| 計測時間 | 12分42秒 | 12分56秒 |
| 移動距離 | 1.282 km | 1.338 km |
| 中央速度 | 6.7 km/h | 6.2 km/h |
| 取得サンプル数 | 90 | 108 |
| 取得間隔（中央値） | 6秒 | 7秒 |
| 取得間隔（最大） | 42秒 | 26秒 |
| **60秒超の欠損** | **0回** | **0回** |
| 移動中の取りこぼし | 0.0% | 0.0% |
| 位置精度（中央値） | 20.1m | 13.5m |
| 位置精度（p95） | 31.5m | 48.8m |
| 電池消費 | **測定不能**（後述） | **測定不能**（後述） |
| 画面ロック中の継続 | 成立 | 成立 |
| アプリ強制終了後の継続 | 成立（ヘッドレス登録が必要） | 成立（ヘッドレス登録が必要） |
| 活動種別の信頼性 | 低い（後述） | 低い（後述） |
| 導入の手間 | Maven Central 配信。追加リポジトリ不要 | 同左。`enableHeadless` 設定項目は無く登録のみ |

**両者とも欠損ゼロで、記録の成否に差は出なかった。**

品質面では tracelet がやや優勢である。同距離でサンプルが2割多く、取得間隔のばらつきも小さく、
精度の中央値も良い。ただし精度の外れ値は tracelet のほうが大きい。
いずれも中心体験の成否を分ける差ではない。

### 参考：条件の揃っていないセッション

対比較の前に取ったもの。**セッション長も経路も揃っていないため、優劣の根拠にはならない。**

| セッション | 提供元 | 時間 | 移動中の取りこぼし |
| --- | --- | --- | --- |
| 08-26 | tracelet | 41分36秒 | 0.0% |
| 08-26 | fbg | 1時間32分 | 20.4% |
| 08-26 | fbg | 13分31秒 | 29.6% |

fbg の値が悪いが、08-27 の対比較では再現しなかった。
経路・時間帯・セッション長のいずれかに起因する可能性が高い。

### 電池消費が測定できなかった理由

1%刻みの残量では、10〜15分の計測で2〜3段階しか動かない。誤差が結論を左右する。

08-27 の対比較では、さらに致命的な交絡があった。

```
fbg       10:00 100%  →  10:08 で 99%  →  終了時 98%
tracelet  10:13  98%  →  10:16 97 → 10:19 96 → 10:24 95%
```

**fbg は最初の8分間、残量が100%のまま動いていない。** 満充電付近で残量計が張り付く現象である。
この区間を含めた見かけの値（fbg 9.4%/時、tracelet 13.9%/時）は比較に使えない。
残量が変化した間隔から概算すると fbg 約13%/時、tracelet 約15%/時となり、差はほぼ消える。

加えて、両者とも `debug: true` / `logLevel: verbose` のまま計測しており、絶対値も過大である。

**電池を判定するには、開始残量を70〜80%程度に揃え、30分以上、デバッグログを切ったビルドで
測り直す必要がある。** 本検証ではそこまで至っていない。

### 活動種別は両ライブラリとも信頼できない

**本検証で最も重要な発見。**

| 実測の中央速度 | プラグイン報告速度 | ライブラリ | 活動種別 | 判定 |
| --- | --- | --- | --- | --- |
| 62.4 km/h | 52.9 km/h | fbg | `walking`（確信度100、23分継続） | 誤り |
| 74.6 km/h | 72.1 km/h | tracelet | `in_vehicle` | 正しい |
| 46.3 km/h | 58.9 km/h | fbg | `still` | 誤り |
| 39.8 km/h | 34.8 km/h | tracelet | `still` | 誤り |

一方、**速度は両者とも正確**であった。

[技術選定](../tech-stack.md) が掲げる「活動種別・移動速度・歩数と距離の整合の3つを組み合わせ、
判定はサーバ側で行う」という方針は正しい。そのうえで、**速度を主たる根拠とし、活動種別は
補助にとどめる**必要がある。活動種別を信じる設計にすると、電車に乗るだけでゲームが進む。

### 権限まわりの挙動

| 権限 | 許可時 | 拒否時 |
| --- | --- | --- |
| 位置（正確な位置・アプリ使用中） | 取得できる | **未検証** |
| 位置（常に許可 / バックグラウンド） | 画面ロック中も継続する | **未検証** |
| 身体活動（ACTIVITY_RECOGNITION） | 活動種別を取得できる | **未検証** |
| 通知（POST_NOTIFICATIONS） | 常駐通知が表示される | **未検証** |
| Health Connect 歩数の読み取り | 取得できる | **未検証** |

**「常に許可」が必須であることは確認済み。** 「アプリの使用中のみ」ではバックグラウンド計測が
成立しない。Android では最初のダイアログで「常に許可」を選べないため、
アプリ側に格上げの導線が必要になる。

**拒否時の挙動は未検証。** Issue の受け入れ条件に含まれるが、本検証では到達していない。

### Health Connect

| 項目 | 結果 |
| --- | --- |
| 歩数を取得できたか | できた（08-23〜08-25 のセッション） |
| 歩数の供給元アプリ | Health Connect 経由。端末には Samsung Health が同居 |
| アプリ側の移動距離との整合 | 日次累計が単調増加し、区間歩数とも整合していた |
| Health Connect 未インストール時の挙動 | **未検証**（Android 16 では OS 組み込みのため再現できず） |

**注意**: 08-26 以降のセッションでは歩数が取得できていない。
検証中にアプリを再インストールした際に権限が失われ、再許可しないまま計測したため。
機能自体は 08-25 までのセッションで動作を確認している。

## 結論

### 中心体験は成立する

**Android 実機で、画面ロック中も位置情報を記録できる。** 同一周回路の対比較で、
両ライブラリとも60秒を超える欠損がゼロだった。歩数も Health Connect から取得できる。

**M1 へ進めない重大課題は見つからなかった。**

### `tracelet` は採用候補として残せる

技術選定の未決事項「`tracelet` が `flutter_background_geolocation` の代替として実用に足るか」
について、**徒歩計測の記録品質では fbg と同等以上**という結果が出た。
無償で置き換えられる見込みがあり、選択肢として保持できる。

ただし **$399 を払うかどうかの判断は、まだできない。** 根拠は次のとおり。

- 対等な条件での比較が1組（各13分）のみ。n が足りない
- 電池消費が測定できていない。省電力の作り込みこそが有償ライブラリの価値であり、
  そこを比較できていない以上、優劣は判断できない
- 端末が Samsung 1台のみ。バックグラウンド計測の成否は OEM の省電力制御に大きく
  左右されるため、1台の結果は一般化できない
- `tracelet` は単独開発者による新しいパッケージであり、長期の保守性は数値に表れない

技術選定が定めた「支払いは配信直前まで先送りする」という方針は維持できる。
**DEBUG ビルドで開発を続けるかぎり費用は発生しない。**

### 設計へ持ち帰るべきこと

1. **徒歩判定は速度を第一の根拠にする。** 活動種別は両ライブラリとも誤る。
2. **アプリの停止を前提に組む。** 計測中にアプリが OS に停止させられるのは例外ではない。
   ヘッドレスでの記録継続と、復帰後にセッションを締め直す仕組みを設計に含める。
3. **「常に許可」への格上げ導線が要る。** 権限が足りないまま計測が成立しないことを、
   利用者に伝える必要がある。
4. **計測の正しさを検証する工数を見込む。** 本検証では、アプリ実装より
   「自分たちの計測が間違っていることに気づく」作業のほうが比重が大きかった。
   M1 の位置情報まわりの見積もりには同種の余裕が必要。

### 残っている検証

| 項目 | 状態 | 備考 |
| --- | --- | --- |
| 権限拒否時の挙動 | **未実施** | 受け入れ条件。特に「使用中のみ」で画面ロック時に止まるかの確認 |
| 電池消費の比較 | **未達** | 開始残量を揃え、30分以上、デバッグログを切って測り直す |
| 対比較の反復 | 1組のみ | n を増やさないと差の有無を判断できない |
| 別メーカー端末 | 未実施 | OEM の省電力制御差を確認できていない |
| Health Connect 歩数の再確認 | 権限未許可 | 機能自体は確認済み |

上2つは、ライブラリの採否を決める前に必要になる。
それ以外は M1 と並行して進められる。
