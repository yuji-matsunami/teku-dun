# Gitワークフローの管理

検証内容を誇張せず、このリポジトリのブランチ、コミット、Pull Requestの規約に従う。

## 適用するルールを確認する

1. 作業前に `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、既存のPRテンプレートなど、リポジトリの指示を読む。
2. [references/git-conventions.md](references/git-conventions.md) を最後まで読む。
3. このスキルよりも、具体的なリポジトリの指示とユーザーの指示を優先する。
4. 規約が曖昧な場合は、最近のブランチ名とコミット履歴を確認する。根拠のないプロジェクト固有ルールを作らない。

## ブランチを準備する

1. `git status`、現在のブランチ、基点にするブランチを確認する。
2. 作業対象外のワーキングツリーの変更を維持する。
3. 作業種別を表すprefixと、作業内容が一目で分かるdescriptionを組み合わせたブランチ名を選ぶ。
4. ユーザーが明示的に依頼し、リポジトリの方針でも許可されている場合を除き、デフォルトブランチへ直接コミットしない。
5. 明示的な許可なしに既存ブランチの改名、削除、リセット、強制更新を行わない。

## コミットを準備する

1. 差分を確認し、無関係な変更を分離する。
2. 現在のコミットに属するファイルだけをステージする。
3. 参照規約で許可されたprefixを使い、1行目に日本語で簡潔なコミットメッセージを書く。2行目以降の詳細は必要に応じて自由に記載する。
4. 可能であれば、コミット前に関連する検証を実行する。
5. 検証結果は「成功」「失敗」「未実行」を区別して正確に報告する。
6. 明示的に依頼されない限り、既存コミットのamend、rebase、force-push、履歴の書き換えを行わない。

## Pull Requestを準備する

1. 基点ブランチから現在のブランチまでの全差分とコミット一覧を確認する。
2. リポジトリにPRテンプレートがある場合はそれを使う。ない場合は [assets/pull_request_template.md](assets/pull_request_template.md) を複製して記入する。
3. 変更結果を表すConventional Commits形式のPRタイトルを使う。
4. Issue番号が判明している場合だけ関連付ける。Issue番号を推測しない。
5. 検証の根拠と利用者に影響するリスクを記載する。未確認のチェック項目にはチェックを付けない。
6. Agent自身がPRの全差分をセルフレビューし、問題があれば修正してからチェックリストへ結果を反映する。
7. 空の任意セクションは、プレースホルダーのまま残さず削除する。
8. 必要な作業が残っている場合やレビュー可能な状態でない場合はDraft PRにする。

## 最終確認を行う

引き渡す前に、次の項目を確認する。

- ブランチ名が選択した形式に従っている。
- 各コミットの目的が明確で、メッセージが規約に適合している。
- PRタイトルと本文が実際の差分を正しく説明している。
- Agentによるセルフレビューを実施し、発見した問題を解消している。
- テストと手動確認の結果が正確に報告されている。
- 秘密情報、認証情報、不要な生成物、無関係な変更が含まれていない。
