# Git運用規約

## 優先順位

明示的なユーザー指示、リポジトリ固有の指示とテンプレート、この文書の既定値の順に適用する。リポジトリの履歴がこの既定値と明確に異なる場合は、確立済みの規約を維持する。

## ブランチ名

作業種別を表すprefixと、作業内容が一目で分かるdescriptionを `/` で区切る。Gitのブランチ名では `:` を使えないため、コミットメッセージとは区切り文字が異なる。

descriptionには小文字のASCII文字とハイフンを使い、対象と操作が分かる具体的なkebab-caseにする。

標準形式:

```text
<prefix>/<具体的な作業内容>
```

Issueがある場合:

```text
<prefix>/issue-<number>-<具体的な作業内容>
```

使用できるprefix:

- `feat`: 新しい動作や機能
- `fix`: 不具合修正
- `docs`: ドキュメントだけの変更
- `refactor`: 動作を変えないコード構造の改善
- `test`: テストだけの変更
- `chore`: リポジトリの保守
- `build`: ビルドシステムや依存関係の変更
- `ci`: 継続的インテグレーションの変更
- `perf`: パフォーマンス改善
- `revert`: 以前の変更の取り消し

```text
docs/add-setup-guide
fix/issue-42-refresh-expired-token
feat/add-csv-export
```

`feat/update`、`fix/bug`、`chore/changes` のように作業内容を特定できないdescriptionは使わない。スペース、アンダースコア、大文字、Issue番号だけの名前も使わない。

## コミットメッセージ

1行目は、作業種別を表すprefixと、日本語で簡潔に書いたコミットメッセージを `: ` で区切る。

```text
<prefix>[(<scope>)][!]: <日本語の簡潔なコミットメッセージ>

[任意の詳細]

[任意のフッター]
```

各コミットの変更種別に対応するprefixを使う。ブランチと異なるprefixでもよい。書式だけの変更には `style` を追加で使用できる。破壊的変更には `!` と `BREAKING CHANGE:` フッターを使う。

1行目のルール:

- 1つの論理的な変更を説明する。
- 日本語で簡潔に書き、末尾に句点を付けない。
- 簡潔に書き、可能であれば72文字以内を目安にする。

2行目以降は任意とする。変更理由、制約、実装の詳細、分かりにくいトレードオフなどを必要に応じて自由に記載する。`Refs: #42` や `Closes: #42` などのIssue参照は、関係が正しい場合だけ記載する。

例:

```text
docs: Git運用規約を追加
fix(auth): 期限切れトークンの更新処理を修正
feat(api)!: ページネーション形式を刷新
```

コミットはアトミックにする。個別にレビューできる場合は、書式変更、リファクタリング、ドキュメント変更、動作変更を混在させない。ユーザーまたはリポジトリの方針で要求されない限り、AIの帰属表記や共同作者トレーラーを追加しない。

## Pull Request

1つのPRには1つの主要な目的だけを含める。次のようなConventional Commits形式のタイトルを使う。

```text
docs: 共有Git運用規約を追加
```

本文には次の内容を記載する。

1. 変更が必要な理由
2. 変更内容
3. 検証方法と結果
4. リスク、互換性への影響、後続作業
5. UIが変わる場合のスクリーンショットまたは録画

PRのマージによってIssueを終了させる場合だけ `Closes #<number>` を使う。終了させない関連付けには `Refs #<number>` を使う。実際に実行して成功したテストだけを成功と記載する。

PRを提出する前にAgent自身が基点ブランチとの差分全体をセルフレビューする。仕様との不一致、バグ、テスト不足、不要な変更、秘密情報、規約違反を確認し、発見した問題を解消してからPRチェックリストへ結果を反映する。

## 安全上のルール

- 明示的な許可なしにデフォルトブランチへ直接コミットしない。
- 秘密情報、ローカル認証情報、`.env` の内容、無関係な生成物を含めない。
- 明示的な許可なしに共有履歴を書き換えたり、force-pushしたりしない。
- ユーザーの無関係な変更を維持し、ファイルを選択的にステージする。
